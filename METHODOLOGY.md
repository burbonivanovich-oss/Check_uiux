# Методология анализа страниц для Claude

Этот документ — рабочая инструкция для Claude в этом репозитории. Он описывает,
как анализировать landing-страницы и пользовательские пути, какие инструменты
использовать, как собирать доказательства и какой формат отчёта возвращать.

Документ дополняет `CLAUDE.md` (общий обзор репозитория). Если возникает
конфликт — `CLAUDE.md` приоритетнее.

---

## 1. Что мы анализируем

Два класса задач, два специализированных агента:

| Задача | Агент | Когда вызывать |
|---|---|---|
| Аудит одной страницы (главная, лендинг, прайс, фича) | `landing-page-analyst` | «разбери лендинг», «почему не конвертит», «CRO-аудит» |
| Прохождение многошагового сценария (регистрация, онбординг, оформление заказа) | `user-journey-analyst` | «пройди регистрацию», «разбери воронку», «где отваливаются пользователи» |

Оба агента описаны в `.claude/agents/`. Запускаются через инструмент `Agent`
с соответствующим `subagent_type`.

---

## 2. Методология аудита (общая для обоих агентов)

### Шаг 0. Уточнение задачи (1 вопрос максимум)

Перед началом убедиться, что известно:

- **URL** страницы или точка входа в сценарий.
- **Целевое действие**: регистрация, демо, покупка, лид-форма, установка.
- **Аудитория и уровень осознанности** (если пользователь может рассказать —
  иначе вывести из самой страницы и явно отметить как допущение).

Если есть `.agents/product-marketing-context.md` — прочитать его для
позиционирования и ICP. Если нет — не блокироваться, работать по тому, что
видно на странице, и явно флагнуть допущения.

Если регистрация создаст реальный биллинг или разошлёт реальные письма —
**остановиться и подтвердить** с пользователем.

### Шаг 1. Захват страницы (capture)

Реальные скриншоты и DOM — это фундамент. Без них не делать выводов.

Минимальный набор для лендинга:

- Десктоп 1440px: above-the-fold + full-page.
- Мобильный 390px: above-the-fold + full-page.
- Снимок accessibility-tree (заголовки, лендмарки, лейблы CTA).
- Сетевые/консольные ошибки, блокирующие запросы, LCP-элемент (если доступно).
- Если есть очевидный главный CTA — кликнуть один раз и захватить следующий
  экран (чтобы аудит покрывал и первый переход, а не только страницу).

Для пользовательского пути: то же самое **на каждом шаге**, плюс время
загрузки/взаимодействия, текст ошибок валидации, лейблы полей, редиректы,
email-гейты.

Артефакты складывать в `./reports/landing-page/<slug>/` или
`./reports/user-journey/<slug>/step-NN-<name>/`.

### Шаг 2. Применить CRO-фреймворк

Загрузить нужный навык (см. таблицу ниже) и пройти по его чек-листу,
ссылаясь на собранные артефакты.

| Тип шага | Навык |
|---|---|
| Лендинг / прайс / фича-страница | `page-cro` |
| Регистрация / signup-флоу | `signup-flow-cro` |
| Любая отдельная форма (лид, контакт, поля чекаута) | `form-cro` |
| Пост-регистрационный онбординг | `onboarding-cro` |
| Психология / убеждение / когнитивная нагрузка | `marketing-psychology` |
| Глубокое понимание ICP | `customer-research` |
| Бутстрап позиционирования | `product-marketing-context` |

Для лендинга минимум покрыть: ясность value proposition (5-секундный тест),
заголовок и подзаголовок, иерархия CTA, социальные доказательства,
обработка возражений, структура и сканируемость, фрикшн (формы, обязательные
поля), доверие и risk reversal, паритет с мобильной версией.

### Шаг 3. Переписать слабую копирайтинг

Для каждого слабого элемента — `before → after` через навык `copywriting`.
Указать использованный фреймворк (PAS, AIDA, BAB, JTBD) и почему он подходит
именно здесь.

### Шаг 4. Отчёт

Структура жёстко фиксирована (см. файлы агентов). Краткие правила:

- **Каждое наблюдение** опирается на доказательство из артефактов
  (скриншот, цитата, лейбл поля, текст ошибки, тайминг).
- **Топ-5 фиксов** — больше не выкатывают. Длинные списки умирают в бэклоге.
- Каждый фикс: проблема → доказательство → рекомендация → before/after →
  усилие (S/M/L) → уверенность (low/med/high).
- Mobile-проблемы — отдельной секцией. Конверсия чаще всего теряется на мобайле.
- Performance/a11y — только то, что влияет на конверсию (LCP, CLS, фокус,
  контраст), а не полный Lighthouse-отчёт.
- В конце — план тестов: 2–3 A/B с приоритетом по ожидаемому эффекту.

### Что запрещено

- Выдумывать клейму, отзывы, метрики, цитаты.
- Рекомендовать тёмные паттерны (фейковая срочность, скрытые цены, bait-CTA).
- Обходить пейволлы, MFA, капчи, гео-блок. Если упёрлись — **остановиться и
  отчитаться**.
- Заполнять формы данными, которые попадут в продакшен пользователя, без явного
  его подтверждения. Использовать заведомо тестовые значения.
- Отдавать рекомендации без доказательной базы из артефактов («улучшите CTA»
  без цитаты текущего CTA — это не рекомендация, это шум).

## 3. Технические возможности: захват страниц

Доступно четыре пути захвата. Агент выбирает первый рабочий из списка по
порядку. Пути не дублируют друг друга — у каждого свои сценарии применения.

### Путь A — локальный `agent-browser` (по умолчанию для локального Claude Code)

Реальный Chromium, скриншоты, клики, accessibility tree, Web Vitals.

```bash
npm i -g agent-browser
agent-browser install --with-deps   # --with-deps только на Linux
agent-browser doctor                # проверка
agent-browser skills list           # доступные команды
```

**Применять, когда**: Claude запущен локально и URL доступен с этого IP.

**Ограничения**: упирается в гео-блок (например, `kontur.ru` отдаёт 403 за
пределами РФ) и в локальную сеть. В облачном Claude Code (claude.ai/code) —
**недоступен**.

### Путь B — Browserbase MCP (`mcp__browserbase__*`)

Облачный браузер с прокси, в т.ч. российским резидентным пулом. Конфигурация
лежит в `.mcp.json`, ключи — в `.env` (см. `.env.example`).

```text
mcp__browserbase__start
mcp__browserbase__navigate
mcp__browserbase__act        # клики, ввод, формы
mcp__browserbase__observe    # читать DOM/состояние
mcp__browserbase__extract    # вытащить структурированные данные
mcp__browserbase__end        # обязательно закрыть сессию (биллинг по минутам)
```

**Применять, когда**:

- Сайт гео-блокирует локальный IP (для российских сайтов нужно поставить RU
  proxy pool в дашборде Browserbase → Project → Proxies).
- Локальный захват упал.
- Пользователь явно попросил прокси-захват.
- Нужны клики/JS-рендеринг в облаке, а GitHub Actions слишком медленный.

**Ограничения**: Web Vitals и сетевую панель MCP не отдаёт — этот пробел нужно
явно отметить в отчёте. Сессии биллятся поминутно — всегда вызывать `end`.

### Путь C — GitHub Actions как fetch-relay (по умолчанию для облачного Claude Code)

Облачный Claude Code (claude.ai/code) сидит в песочнице, чей outbound
allowlist — это только `github.com`, `registry.npmjs.org`, `api.anthropic.com`.
`agent-browser`, Browserbase, Jina Reader — недостижимы. Решение: использовать
`github.com` (есть в allowlist) как relay через GitHub Actions.

**Как работает**:

1. Агент кладёт `requests/<timestamp>-<slug>.json` со схемой
   `{url, slug, engine?, user_agent?, accept_language?, locale?, timezone?}`
   через `mcp__github__create_or_update_file`.
2. Push триггерит `.github/workflows/fetch-page.yml`, который запускает
   `scripts/fetch.mjs` (Playwright + headless Chromium с реалистичными
   заголовками, локалью `ru-RU`, таймзоной `Europe/Moscow` по умолчанию).
3. Скрипт ждёт, пока разрешатся JS-челленджи (DataDome / Cloudflare / Akamai),
   снимает desktop и mobile скриншоты, сохраняет рендер.
4. Результат коммитится в `samples/<slug>/`:
   - `page.html` — полный отрендеренный HTML
   - `desktop-above-fold.png`, `desktop-full.png`
   - `mobile-above-fold.png`, `mobile-full.png`
   - `status.json` со схемой `{ok, http_status, size_bytes, challenged, error, ...}`
5. Агент опрашивает `samples/<slug>/status.json` через
   `mcp__github__get_file_contents` (раз в ~15с, до 3 минут). При `ok: true` —
   читает `page.html` и скриншоты.
6. Обработанный request переезжает в `requests/processed/`.
7. `[skip ci]` в коммит-сообщении воркфлоу защищает от петель.

**Применять, когда**: Claude запущен в облаке (claude.ai/code).

**Что даёт**:
- Отрендеренный HTML для любого публичного URL (Playwright выполняет JS, SPA и
  челленджи отрабатывают).
- Desktop + mobile скриншоты (above-fold и full-page).
- Детектор bot-челленджа (`challenged: true` в `status.json`), чтобы агент не
  принял капчу за лендинг.
- Работает без локальной установки и сторонних API.
- Бесплатно (в пределах GitHub Actions free tier; одна выборка ~60–90с
  раннер-времени).

**Чего не даёт**:
- Web Vitals (нужно отдельно прокидывать Performance Observer).
- Многошаговые клик-флоу: каждый шаг — отдельная страница (отдельный request).
  Подходит, если шаги доступны как обычные GET-урлы (`/signup`, `/pricing`).
  Если флоу — JS-driven форма с настоящими кликами, то **остановиться и
  рекомендовать Путь A или B**.

**Однократная настройка** (если Actions ещё не включены):

1. Settings → Actions → General.
2. Actions permissions → разрешить.
3. Workflow permissions → **Read and write**.

**Ручной запуск** (без агента): Actions → fetch-page → Run workflow → URL и
slug. Результат окажется в `samples/<slug>/`.

### Путь D — ручная вставка HTML

Последний вариант. Попросить пользователя открыть страницу в своём браузере,
View Source, вставить HTML в чат. Использовать только если A, B, C недоступны.

### Если все пути упали

Остановиться. Сообщить пользователю, какой путь и почему не сработал.
**Не сочинять контент страницы.**

## 4. Структура репозитория и куда что складывать

```
.claude/
  agents/
    landing-page-analyst.md       # агент аудита одной страницы
    user-journey-analyst.md       # агент прохождения сценариев
  skills/                         # автоматически активируемые навыки
    page-cro/                     # CRO для лендинга
    form-cro/                     # CRO для форм
    signup-flow-cro/              # CRO для регистрации
    onboarding-cro/               # CRO для онбординга
    copywriting/                  # копирайтинг (PAS/AIDA/BAB/JTBD)
    customer-research/            # исследование аудитории
    marketing-psychology/         # психология убеждения
    product-marketing-context/    # бутстрап позиционирования (запускать первым)
    agent-browser/                # драйвер реального браузера

.github/workflows/
  fetch-page.yml                  # GitHub Actions relay для облачного Claude

scripts/
  fetch.mjs                       # Playwright-фетчер, который вызывает воркфлоу

requests/                         # очередь задач на захват для Пути C
  README.md                       # формат request-файла
  processed/                      # архив обработанных запросов

samples/                          # сюда фетчер кладёт сырые захваты
  <slug>/
    page.html
    desktop-above-fold.png
    desktop-full.png
    mobile-above-fold.png
    mobile-full.png
    status.json

reports/                          # финальные отчёты для пользователя
  landing-page/<slug>/
    REPORT.md
    desktop-*.png
    mobile-*.png
  user-journey/<slug>/
    REPORT.md
    step-01-landing/, step-02-signup/, ...

.mcp.json                         # конфигурация Browserbase MCP
.env.example                      # шаблон ключей (BROWSERBASE_*, GEMINI_API_KEY)
.gitignore                        # игнорим .env и тяжёлые скриншоты в reports/
CLAUDE.md                         # обзор репозитория
METHODOLOGY.md                    # этот файл
```

`reports/`, `samples/`, `requests/`, `requests/processed/` хранят `.gitkeep`
для устойчивости структуры. Пуш с `.png` в `reports/` игнорится `.gitignore` —
скриншоты живут только в `samples/` (откуда их кладёт fetcher) и локально у
пользователя.

## 5. Чек-лист перед стартом

Перед запуском любого агента:

- [ ] URL и целевое действие зафиксированы.
- [ ] Понятно, в каком окружении работает Claude (локально / облачно) — это
      определяет путь захвата.
- [ ] Если нужен Browserbase: ключи в `.env` подгружены (`set -a && source .env
      && set +a` перед запуском Claude Code).
- [ ] Если нужен GitHub Actions relay: Actions включены и имеют write-доступ.
- [ ] Если флоу включает регистрацию с реальным биллингом или письмами —
      получено явное согласие пользователя.

---

## 6. Чек-лист после захвата

- [ ] `samples/<slug>/status.json` есть и `ok: true` (для Пути C).
- [ ] Скриншоты не пустые и не показывают капчу (`challenged: false`).
- [ ] HTML > 1KB и содержит реальный контент, а не «Just a moment...».
- [ ] Если что-то из этого не так — отчёт об этом, а не выдумка.

---

## 7. Чек-лист отчёта

- [ ] Лежит в `./reports/<тип>/<slug>/REPORT.md`.
- [ ] Каждое наблюдение цитирует артефакт.
- [ ] Топ-5 фиксов с before/after, effort, confidence.
- [ ] Mobile отдельной секцией.
- [ ] План тестов в конце (2–3 шт).
- [ ] Без выдуманных цифр и фейковых отзывов.
- [ ] Без тёмных паттернов в рекомендациях.
